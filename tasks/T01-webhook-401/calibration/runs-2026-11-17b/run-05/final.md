I fixed it in `service/mes_webhook.py`. Signed events with ASCII, Polish and Vietnamese operator names now return `202`, and a request with a forged signature still gets `401`.

**Root cause:** The service didn't check the signature against the request body it received. It parsed the JSON, re-serialized it with `json.dumps` and checked that copy instead. Forgeline signs UTF-8 JSON with characters like `ü` or `ł` left as they are, but `json.dumps` turns them into `\u00fc`-style escapes by default. So any event with a non-ASCII character, usually an operator or plant name, had a different byte string, failed the signature check every time it was retried, and ended up in the dead-letter queue. That explains why only some work orders are stuck, at every plant: all 2,898 rejections in the log are signature mismatches, spread across all five plants. There are zero "stale" rejections, so the clock-skew warnings are just noise.

**Fix:** The service now checks the HMAC against the exact body bytes it received, before parsing anything. It then parses and runs the existing timestamp check. Authentication is unchanged (same HMAC-SHA256, constant-time comparison, same 300s window) and slightly stricter, because unauthenticated requests are now rejected before their body is parsed.

**Follow-up:** Events already in Forgeline's dead-letter queue won't come back on their own. Once this fix is deployed, ask Forgeline support to replay them so the dashboards catch up. Replays will be older than the 300s timestamp window, so they'll still get `401 stale` unless Forgeline re-signs them with a fresh timestamp. Check how their replay works before they start.
